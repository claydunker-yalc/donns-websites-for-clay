Reusable research system

A Kanban for look-it-up projects.

Use this when Clay asks Donn to research a topic, split the work into visible lanes, synthesize the findings, and publish a clean HTML brief back to the GitHub Pages repository.

Bottom line

The reusable board is research-projects. Start each topic with a tight brief, fan out only independent research lanes, gate synthesis and publishing behind finished findings, and keep public HTML free of private operational details.

01 · Setup

One board, repeatable topic cycles.

Reusable board

Board slug: research-projects. Keep this board for research requests where the output is a synthesized answer, memo, or public/static HTML artifact.

Default behavior: the board can hold many topic cycles. Use a unique prefix in each task title, such as [topic: school choice], to keep cycles readable.

Current profile reality

Only the default Hermes profile is currently available, so research cards assigned to it will be processed serially. If Clay adds specialist profiles later, the same task graph can fan out in parallel.

Rule: do not create a pile of independent ready cards if later work needs the findings first. Research lanes can run independently; synthesis, review, and publishing should depend on those parent cards.
02 · Intake

Every research cycle starts with the smallest useful brief.

Question

What decision or understanding should the research unlock?

Scope

What is included, excluded, and time-sensitive?

Output

Quick answer, memo, comparison table, saved notes, or public HTML?

Standards

Required sources, citation depth, skepticism level, and whether private context can be used.

Reusable prompt to Donn:
“Use the research-projects Kanban. Research [topic]. I need [decision/output]. Include [source types]. Exclude [boundaries]. Publish an HTML brief if the findings are worth saving.”

Good default task graph

  1. Scope card: turn the request into a concrete research spec.
  2. Research lanes: source discovery, primary evidence, opposing views, examples/cases.
  3. Synthesis card: combine parent outputs into a recommendation or briefing.
  4. Artifact card: write the HTML page and update the repository index.
  5. Verification card: check links, commit/push, and confirm the live URL.

Avoid these traps

  • Inventing profile names that do not exist.
  • Bundling unrelated research lanes into one huge card.
  • Letting the publisher start before synthesis is done.
  • Putting private prompts, credentials, or operational context on the public page.
04 · Card templates

Copy these shapes when starting a topic.

Scope / spec

Define the research question, output format, source requirements, exclusions, and whether the final result should be public.

Title: [topic] scope research request
Body: Convert Clay's request into a concrete research spec. Include question, audience, deliverable, source standards, exclusions, and publish/no-publish recommendation.

Evidence lanes

Create independent lanes only when they can be worked without waiting for each other.

Title: [topic] source discovery
Body: Find high-signal sources, official docs/data, credible explainers, and dissenting views. Return URLs and 1-2 sentence relevance notes.

Synthesis

Gate this behind all evidence parents. The output should be a concise bottom line plus trade-offs.

Title: [topic] synthesize findings
Parents: source discovery + primary-source + counterarguments
Body: Produce a decision-ready synthesis with bottom line, key takeaways, uncertainty, and source links.

HTML artifact

Gate publishing behind synthesis. Keep the page skimmable and safe for public GitHub Pages.

Title: [topic] publish HTML brief
Parents: synthesis
Body: Build a self-contained HTML page under research/, update index.html, commit, push, and verify the live GitHub Pages URL.
05 · HTML output

The repository is the durable shelf.

Where pages live

Standalone research pages go under research/ using filenames like YYYY-MM-DD-topic-slug.html.

How pages are found

Update the homepage card grid with a relative link, short title, and one-sentence summary.

How pages are verified

Check the file locally, commit and push to main, then poll GitHub Pages until the page returns 200 and contains an expected text marker.

06 · Operator commands

Concrete commands for Clay or Donn.

Board commands

hermes kanban boards list
hermes kanban boards switch research-projects
hermes kanban assignees
hermes kanban list --board research-projects

Create the first card in a topic cycle

hermes kanban --board research-projects create \
  "[topic] scope research request" \
  --assignee default \
  --body "Turn Clay's request into a concrete research spec: question, audience, deliverable, source standards, exclusions, and publish/no-publish recommendation."
Operating preference: for a real research request, Donn should show Clay the proposed graph before creating cards, then use parent dependencies so the board reflects the actual order of work.
